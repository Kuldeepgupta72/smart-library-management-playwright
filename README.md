# Framework Architecture

Playwright + TypeScript automation framework covering **two independent
applications** from one repo:

1. **`automationexercise.com`** — a plain Playwright/TypeScript UI suite
   (`tests/ui/`), Page Object Model (POM) with a locators/behavior split.
2. **Library Management System** (`http://localhost:5050`, run locally) — a
   Gherkin/BDD suite (`features/` + `src/steps/`) built with
   [`playwright-bdd`](https://github.com/vitalets/playwright-bdd), reusing
   the exact same POM conventions as suite 1.

Both suites share one environment-driven configuration layer
(`ConfigManager`), one `BasePage` behavior contract, and the same
locators/behavior split — the BDD suite is an *extension* of the existing
architecture, not a parallel one.

## Layers, and why each exists

### 1. Configuration layer — `ConfigManager.ts`

A singleton (`ConfigManager.getInstance()`) that reads `process.env` (loaded
from `.env` via `dotenv`), validates an `ENV` value (`dev` | `qa` |
`staging`), and resolves environment-prefixed variables
(`DEV_BASE_URL`, `QA_BASE_URL`, ...) plus `LIBRARY_BASE_URL` into one typed
`EnvironmentConfig` object. It throws early if a required URL is missing,
instead of failing later with a confusing navigation error.

`playwright.config.ts` calls `ConfigManager.getInstance().getBaseUrl()` to
set Playwright's `use.baseURL` for the `automationexercise.com` suite — this
is what lets those page objects call `this.navigate('/')` with a relative
path. The Library suite targets a **different** origin, so its page objects
never rely on the global `baseURL`; they pass the full absolute URL from
`envConfig.libraryBaseUrl` instead (see `LibraryBasePage` below).

`envConfig` (a pre-resolved `EnvironmentConfig` instance) is exported
directly from `ConfigManager.ts`, so it can be injected as a fixture without
every test/page object importing `ConfigManager` itself.

### 2. Fixtures layer — two `test` objects

| File | Built on | Used by |
|---|---|---|
| `src/fixtures/baseTest.ts` | `@playwright/test`'s `test` | `tests/ui/*.spec.ts` |
| `src/steps/bddTest.ts` | `playwright-bdd`'s `test` | `src/steps/*.steps.ts` |

Both wrap their base `test` with `test.extend<Fixtures>()`, declaring one
fixture per dependency a spec/step might need. Specs/steps destructure only
what they need (e.g. `async ({ homePage, cartPage }) => {...}`) instead of
constructing page objects manually.

**Why two `test` objects instead of one:** `playwright-bdd`'s `createBdd()`
requires a `test` that descends from its own `test` export — a `test`
built purely from `@playwright/test` (like `baseTest.ts`) is rejected at
`bddgen` time. Since the two BDD projects can't be unified without either
breaking the existing non-BDD suite's `test` chain or coupling it to
`playwright-bdd`, `bddTest.ts` re-declares the same fixture-registration
pattern on top of `playwright-bdd`'s `test`. `baseTest.ts` is untouched by
this — it still only knows about `@playwright/test`.

`baseTest.ts` fixtures:

| Fixture | Provides |
|---|---|
| `homePage` | A `HomePage` instance bound to `page` |
| `cartPage` | A `CartPage` instance bound to `page` |
| `loginPage` | A `LoginPage` instance bound to `page` |
| `libraryBooksPage` | A `LibraryBooksPage` instance bound to `page` |
| `libraryMembersPage` | A `LibraryMembersPage` instance bound to `page` |
| `libraryIssuePage` | A `LibraryIssuePage` instance bound to `page` |
| `libraryReturnPage` | A `LibraryReturnPage` instance bound to `page` |
| `dataLoader` | A `DataLoader` instance |
| `envConfig` | The resolved `EnvironmentConfig` |

`bddTest.ts` fixtures: the same 4 Library page objects, `dataLoader`,
`envConfig`, plus one BDD-only fixture:

| Fixture | Provides |
|---|---|
| `state` | A fresh, empty `ScenarioState` object per scenario — the only way step definitions (which don't share closures like Cucumber's "World") pass data from one step to the next within the same scenario |

### 3. Page Object layer — `src/pages/`

**`BasePage.ts`** — the parent class every page object (both suites)
extends. Holds behavior that has nothing to do with any single page:

| Method | Signature | Purpose |
|---|---|---|
| `navigate` | `(path?: string) => Promise<void>` | `page.goto(path)`, default `'/'` |
| `fill` | `(locator: Locator, value: string) => Promise<void>` | Thin wrapper over `Locator.fill` |
| `click` | `(locator: Locator) => Promise<void>` | Thin wrapper over `Locator.click` |
| `waitForELement` | `(locator: Locator, timeout?: number) => Promise<void>` | Explicit visibility wait |
| `screenshot` | `(name: string) => Promise<Buffer>` | Full-page screenshot under `reports/screenhsots` |
| `dismissOverlaysIfPresent` | `() => Promise<void>` | Best-effort close of an ad/overlay button, swallows errors |

#### automationexercise.com page objects

**`HomePage.ts`** (product-listing page)
- `open(): Promise<void>` — navigates to `/`
- `addProductToCart(index: number): Promise<void>` — clicks the *n*-th
  product card's always-visible "Add to cart" button
- `continueShopping(): Promise<void>` — dismisses the post-add-to-cart modal
- `goToCart(): Promise<void>` — clicks the header cart link

**`CartPage.ts`**
- `proceedToCheckout(): Promise<void>`
- `continueOnCart(): Promise<void>`

**`LoginPage.ts`**
- `goto(): Promise<void>` — navigates to `/login`, dismisses overlays
- `login(email: string, password: string): Promise<void>`
- `expectLoginError(): Promise<void>`
- `expectLoggedInAs(username: string): Promise<void>`

#### Library Management System page objects

**`LibraryBasePage.ts`** (abstract, extends `BasePage`) — the app is a
single-page, tab-based UI, so every Library page object "opens" the same
way: navigate to the app root, then click a tab. That's centralized here:

- `protected openTab(tabSelector: string): Promise<void>` — `this.navigate(envConfig.libraryBaseUrl)` (the **full absolute URL**, read from the shared `envConfig` singleton — never hardcoded) then `this.click(this.page.locator(tabSelector))`

**`LibraryBooksPage.ts`** (Books tab)
- `open(): Promise<void>`
- `addBook(title: string, author: string, isbn: string): Promise<void>`
- `expectDuplicateIsbnError(): Promise<void>` — asserts `#book-error` text is exactly `"A book with this ISBN already exists."` (KAN-29)
- `expectBookAddedSuccessfully(isbn: string): Promise<void>` — asserts a row containing `isbn` is visible in the books table
- `countBookRows(isbn: string): Promise<number>` — counts matching rows, used to prove a duplicate-ISBN attempt did **not** add a second row

**`LibraryMembersPage.ts`** (Members tab)
- `open(): Promise<void>`
- `addMember(name: string, email: string): Promise<void>`
- `expectInvalidEmailError(expectedMessage?: string): Promise<void>` — asserts `#member-error` text; defaults to `"Invalid email format."` (KAN-30) but accepts an override, since the app returns a different message (`"Name and email are required"`) for a blank/whitespace-only email
- `expectMemberAddedSuccessfully(email: string): Promise<void>`
- `countAllMemberRows(): Promise<number>` — total row count, used as a before/after guard to prove a rejected add didn't create a row

**`LibraryIssuePage.ts`** (Issue Book tab)
- `open(): Promise<void>`
- `issueBook(bookTitle: string, memberName: string): Promise<void>` — the `<select>` options are rendered as `"<title> — <author>"`, so this resolves the matching `<option>` by substring on `bookTitle`, reads its `value`, and selects by value (an exact-label match on the title alone would never hit)
- `expectDueDateShown(expectedDueDate?: string): Promise<void>` — there is no dedicated due-date element; the due date is shown inside the shared `#message-banner` toast (`"Book issued successfully. Due date: YYYY-MM-DD"`) — KAN-5

**`LibraryReturnPage.ts`** (Return Book tab)
- `open(): Promise<void>`
- `expectDueDateInLoansList(bookTitle: string, expectedDueDate: string): Promise<void>` — the loans table has no per-column class, so the due-date cell is addressed positionally (`Book | Issued To | Issued Date | Due Date | Action` → 4th `<td>`) — KAN-5

Every page class takes only a `Page` in its constructor (matching the
existing `HomePage`/`CartPage`/`LoginPage` style exactly), builds its
`Locator`s once, and exposes only **behavior** methods — no spec or step
file reaches into raw selectors directly.

### 4. Locators — `src/pages/locators/`

One file per page, exporting a plain object of raw selector strings only.
Deliberately separated from the page class: the page class answers *"what
can a user do on this page"*, the locator file answers *"where is that
element."* A selector rename never touches behavior code, and vice versa.

Library locators were written as placeholders first, then **verified
against the live app** at `http://localhost:5050` (see `Verified locator
notes` below) — every file now reflects the real rendered HTML/DOM, not a
guess.

### 5. Utilities — `DataLoader.ts`

Loads and parses a JSON fixture file from `src/data/<file>.json` given just
a filename (e.g. `dataLoader.load<LibraryTestData>('library-testdata.json')`),
throwing a clear error if the file doesn't exist. Deliberately simple — no
brand/environment sub-folders.

### 6. Test data — `src/data/`

- `users.json` — `invalidUser` credential pair for the login-error spec
- `library-testdata.json` — `validBook`, `duplicateIsbnBook`, `validMember`,
  and an `invalidEmails[]` array (`case`, `email`, `expectedError`) driving
  the email Scenario Outline's Examples table

### 7. Specs and BDD steps

- `tests/ui/*.spec.ts` — plain Playwright specs; import `{ test, expect }`
  from `baseTest.ts`, destructure fixtures, read as a sequence of business
  actions. No raw locators, no hardcoded URLs.
- `src/steps/library.steps.ts` — `Given`/`When`/`Then` implementations for
  `features/library-batch1.feature`, built via `createBdd(test)` where
  `test` comes from `bddTest.ts`. Each step destructures page-object
  fixtures plus `state` (see below) and `dataLoader`.

#### Sharing state between BDD steps

Cucumber's "World" object doesn't exist in `playwright-bdd`; instead, a
`state: ScenarioState` fixture (declared in `bddTest.ts`) is created fresh
per scenario and passed into every step. A `Given` step writes to it (e.g.
the ISBN it just created), a later `Then` step reads it back:

```ts
export interface ScenarioState {
  isbn?: string;
  bookTitle?: string;
  memberName?: string;
  memberEmail?: string;
  memberRowCountBefore?: number;
}
```

#### One error-checking step, two page objects

`Then('I should see the error {string}', ...)` is reused by both the
duplicate-ISBN scenario and the invalid-email Scenario Outline (the feature
file only asserts the message text, not which form produced it). The step
dispatches by inspecting the message itself:

```ts
if (message.toLowerCase().includes('isbn')) {
  await libraryBooksPage.expectDuplicateIsbnError();
} else {
  await libraryMembersPage.expectInvalidEmailError(message);
}
```

## Gherkin/BDD setup (`playwright-bdd`)

`playwright.config.ts` calls `defineBddConfig({ features:
'features/**/*.feature', steps: ['src/steps/**/*.ts'] })`, which compiles
every `.feature` file into a `.spec.js` file under `.features-gen/` (a
generated, gitignored directory) and returns that directory as a `testDir`.
The Playwright config then declares **two separate projects** so neither
suite affects the other's `testDir`, fixtures, or execution:

```ts
projects: [
  { name: 'chromium', testDir: './tests', use: {...devices['Desktop Chrome']} },
  { name: 'library-bdd', testDir: libraryBddTestDir, use: {...devices['Desktop Chrome']} },
]
```

`package.json` scripts:
- `npm run bddgen` — regenerates `.features-gen/` from the current
  `.feature` files and step definitions (must run — or be chained — before
  `library-bdd` tests, since Playwright only ever sees the generated specs)
- `npm run test:library-bdd` — `bddgen` then `playwright test
  --project=library-bdd`

## Feature file — `features/library-batch1.feature`

Covers three "Batch 1" enhancements to the Library app:

| Ticket | Behavior | Scenario(s) |
|---|---|---|
| KAN-5 | Issuing a book computes `due_date = issued_date + 14 days`, shown in the success toast and as a column in the loans list | *Successfully issue a book...*, *Due date appears correctly in the loans list* |
| KAN-29 | Adding a book with a duplicate ISBN shows `"A book with this ISBN already exists."` and does not add it | *Adding a book with a duplicate ISBN...*, *Successfully add a book with a unique ISBN* (positive case) |
| KAN-30 | Adding a member with an invalid email shows `"Invalid email format."` and does not add it | Scenario Outline over 3 cases (missing `@`, missing domain, blank), *Successfully add a member...* (positive case) |

A `Background` (`Given a unique book with a unique ISBN exists in the
library`) seeds a fresh book per scenario using a `Date.now()`-suffixed
title/ISBN, so scenarios are independent and safe to re-run against the
same persistent (SQLite-backed) app instance without colliding on old data.

### Verified locator notes

The Library app was inspected live at `http://localhost:5050` (its
`index.html` and `app.js`) to replace the original placeholder selectors:

- Tab buttons have no per-tab IDs — they're `<button class="tab-btn"
  data-tab="books">` etc., so tabs are selected via
  `.tab-btn[data-tab="..."]`.
- "Add" buttons are plain `<button type="submit">` inside each form, not
  `#add-book-btn`/`#add-member-btn` — selected via `#add-book-form
  button[type="submit"]` / `#add-member-form button[type="submit"]`.
- There is no dedicated due-date element — it only appears in the shared
  `#message-banner` toast after issuing.
- The loans table has no per-column classes — the due-date cell is
  addressed positionally (`td:nth-child(4)`).
- Issue-tab `<select>` options are labeled `"<title> — <author>"`, so
  `LibraryIssuePage.issueBook()` matches by substring on the title rather
  than an exact label.

### Two bugs found only by running against the live app

1. **Empty email is unreachable.** The email `<input>` has the HTML
   `required` attribute, so a truly empty value never submits — the
   browser blocks it before the app's own JS (and its `"Invalid email
   format."` check) ever runs. The Scenario Outline uses a `<blank>`
   sentinel instead, which the step definition maps to a single space: it
   passes the browser's `required` check but is empty once trimmed
   server-side, correctly exercising the app's real `"Name and email are
   required"` error path.
2. **A persistence race in the duplicate-ISBN scenario.** The `Background`
   step submitted the first "add book" request without waiting for it to
   actually persist before the very next step tried to add a duplicate —
   under parallel-worker load, both POSTs could race past the server's
   uniqueness check. Fixed by asserting the first book is visible in the
   list (`expectBookAddedSuccessfully`) before any later step acts on it;
   the same fix was applied to the "member exists" step ahead of issuing.

## Running tests

- `npm test` — run everything (both projects) against the default (`dev`)
  environment
- `npm run test:dev` / `test:qa` / `test:staging` — run against a specific
  environment (`ENV` env var, resolved by `ConfigManager`)
- `npm run test:ui` — `automationexercise.com` UI specs only (`tests/ui`)
- `npm run test:library-bdd` — regenerate and run the Library BDD suite
  (requires the app running locally at `http://localhost:5050`)
- `npm run bddgen` — regenerate `.features-gen/` without running tests
- `npm run test:headed` / `test:debug` — headed / step-through debugging
- `npm run report` — open the last HTML report (`reports/html-report`)
- `npm run typecheck` — `tsc --noEmit` across `src/`, `tests/`, `features/`
  step definitions, and `playwright.config.ts`
